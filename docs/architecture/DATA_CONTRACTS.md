# Practice Desk — domain and trust contracts

This guide expresses **stable design invariants**. Use the source TypeScript validators, schemas and current machine capability contract for exact fields and numeric bounds. Never manufacture fields from examples or infer examination law from an exam title.

## Question, answer and paper

- Six validated kinds: `single-choice`, `multiple-select`, `numeric-entry`, `true-false`, `matching` and `free-response`. Keys and allowed responses must match their declared type. Single/multiple options, numeric tolerances, matching cardinality/uniqueness and rich/media references are constrained.
- An exam package identifies the paper, source/edition, underlying questions and immutable revisions, keys, section policies, time/navigation rules, explicit candidate tools and stimuli. Candidate tools are hash-bound paper policy: availability is never inferred from an exam name. The current calculator profile is `candidateTools.calculator = "basic-v1"`; any intentional semantic change requires a new profile/version. Generic paper-authorised reference resources are declared through `candidateTools.references` as stable resource ID + SHA-256 bindings. The package carries the corresponding candidate-visible rich reference documents and any verified local assets; every declared binding must have exactly one matching resource, and changing its content changes the executable paper identity. The executable paper must retain exactly what the candidate attempted.
- Scores use the **declared paper/key policy**; correct, incorrect, unanswered and partial components obey bounds. Partial score cannot exceed a fully correct question, and a manually assessed written answer is **not silently machine-graded**.
- The printer/original `Source` and editorial `Reviewed` editions have distinct identities and changes. Every Reviewed paper revision hash-binds the exact Source paper/key revision IDs; unbound or ambiguous pairing is invalid. Source comparisons use only the current schema-3 representation, retaining comparable MCQs beside individually unavailable question types and hashing candidate-visible wording/options/media/stimuli plus any paper-level candidate-reference context, but not private explanations or classification tags. A changed candidate reference makes the affected Source/Reviewed semantic comparison conservative rather than pretending the candidate saw identical context. The advisory Source comparison never changes scored History. **6 Oct CGL Q62:** original invalid/excluded, reviewed caution scores publisher B.
- A conceptual question ID may have multiple revisions; do not equate a question revision count with underlying distinct-question count.

## Candidate calculator semantics

`basic-v1` is a frozen behavioural contract, not a generic promise that may silently change. Binary operators execute immediately left-to-right; `=` executes one pending operation once; `%` is unary `x/100`; square root and reciprocal are unary; division by zero, reciprocal of zero and square root of a negative value produce `Error`. Candidate entry is capped at 15 digits (excluding sign/decimal point), finite results are displayed through 12 significant digits, and `C` clears the active calculation while preserving the single memory register. Memory operations are `MC/MR/MS/M+/M-`; non-finite arithmetic fails safely. The pure state machine lives in the domain layer; HTML, keyboard/focus behavior and persistence are adapters around that contract.

Calculator display, pending operation, memory and open/closed state are recoverable **candidate workspace scratch state**. They are validated and stored separately from attempts, frozen content, answers, scoring and portable History backups. A completed or explicitly deleted attempt clears that scratch state. Failure or corruption of scratch storage must reset the calculator safely and must never block or alter the exam record.

## Candidate annotations and scratch evidence

Candidate eliminations and highlights are **candidate-owned attempt evidence**, not authored question content and not a `CandidateResponse`. They therefore cannot affect answer legality, scoring, source/review comparison, FSRS ratings, notebook scheduling or the immutable question/key hashes.

- Option elimination is recorded against the exact frozen `questionRevisionId` and stable `OptionId`; displayed A/B/C positions are not identities. Candidate-facing strike/restore controls are siblings of answer inputs, so elimination never selects, clears, disables or otherwise changes a `CandidateResponse`. The state survives ordinary attempt persistence/reload through `candidateScratch`.
- `Next unanswered` and `Next flagged` are derived navigation affordances, not new navigation authority. They choose the next matching destination in authored paper order (wrapping only when legal) and every candidate target must pass the same engine `canNavigateToQuestion()` predicate used by ordinary `NAVIGATE`. Forward-only papers therefore cannot wrap backward; sectional/sequential-locked papers cannot jump across a locked section; completed sections cannot be re-entered.
- Highlights are anchored to the exact frozen candidate-visible surface. The candidate UI exposes question prompts, textual single/multiple-choice options, eligible stimulus passage/case text, table cells and image/chart captions. Option labels and strike controls are outside the text anchor; option identity remains the stable authored `OptionId`. Plain text uses bounded canonical-source offsets. Rich text uses structural paths into text leaves plus local start/end offsets: paragraph/heading `block → inline`, list `block → item → inline`, table `block → row → column → inline`. Authoring bold/emphasis/underline/list/table structure remains intact around the decoration. Inline/display KaTeX and images expose no text-leaf path and therefore stay atomic/non-highlightable. A cross-leaf selection is persisted as multiple source fragments, never one flattened DOM/HTML range.
- Scratch validation rejects unknown questions/options/stimuli, duplicate IDs, unsupported surfaces and out-of-range anchors. It is stored on the attempt separately from the response/timing state.
- Candidate scratch survives completion and checksum-verified History backup so an explicit later review/handoff can use it. It is deleted with the attempt. This is intentionally different from **transient workspace scratch** such as calculator state, unsaved multiple-select/matching drafts and transient written-response drafts, which terminal persistence clears.
- Learner-focus/personalisation exports do not expose candidate scratch. **Attempt / Study Handoff** is a separate, bounded, single-completed-attempt export; candidate annotations are included only through an explicit opt-in control and are resolved back to exact frozen-source excerpts rather than DOM offsets.

## Candidate reference resources

A candidate reference is a generic paper-authorised rich resource, not a domain-specific `labValues`, formula-sheet or statute schema. The same contract can represent permitted laboratory values, formula sheets, statutory extracts, constants, tables or other supplied examination references using the existing restricted rich-document model (text, lists, tables, maths and verified local images).

The paper binds only `{id, contentHash}` entries in `candidateTools.references`; the package owns the validated resources. A reference hash covers its canonical rich document/metadata and the SHA-256 digests of every referenced image, so changing reference-only image bytes also changes the paper binding. Attempt start freezes the exact resources and any reference-only assets into the immutable attempt snapshot. Reference figures reuse the same verified local image zoom/pan viewer as question media rather than creating a second viewer path. Hashes establish byte/content consistency, not that a reference is officially permitted or factually correct; the candidate panel therefore describes them as paper-supplied and explicitly does not certify external-exam permission. Source/provenance verification remains external.

**Current implementation boundary:** Pass A defines authoring/publication/import/freeze/persistence contracts; Pass C surfaces bounded candidate highlighting; Pass D now surfaces the generic reference panel. The trigger exists only when the frozen paper declares `candidateTools.references`. The panel resolves the paper bindings against the exact frozen `candidateReferences` inventory, renders only those candidate-visible resources/assets through the restricted rich renderer, and provides a bounded **120-character local query**, AND-token matching across title/category/keywords/rich text/math linear text/image alt text, plus an exact authored-category filter. Query, category and current-selection state are transient UI state and are reset rather than persisted/backed up. Reviewer-only keys/explanations/disputes never become reference resources merely because related package data exists. No exam-specific runtime inference is permitted.

## Exam lifecycle and candidate-facing security

1. Validate and preflight the source package; freeze paper/key/media/policy/edition and source-reference IDs **at start**, not on post-submit rendering.
2. Accept legal `answer`, `clear`, `flag`, `navigate`, `pause`, `resume`, `submit` and `expiry` events for the selected navigation/timer policy. The frozen paper supplies the time budget; frozen `AttemptMode` supplies enforcement: exam simulation is hard-deadline, while practice modes may continue into advisory overtime. Prevent post-deadline edits in hard mode, double counting, clock rollback and illegal cross-section responses.
3. Candidate content is narrower than reviewer/answer-key data. Solutions, explanations, editorial disputes, answer-only media and privileged annotations must not leak before the permitted review boundary.
4. On completion, store the exact result/ledger. A later correction or notebook rating must not modify those frozen marks.
5. Preserve raw measured timing/event evidence. Per-question `postDeadlineMs` is foreground exposure after an advisory budget, not wall-clock paper overtime; do not invent per-question limits, typing speed, semantic quality scores or mastery from timing.

## Written responses and result evidence

- Free-response text remains manual/pending for substantive assessment. Automated marks never silently score relevance, factual quality, structure or language; optional self-assessed marks/notes remain separate from the immutable machine score.
- `wordLimit` is optional and advisory. Omission means no authored target; no implicit 300-word limit is inserted. Results derive word count with the same canonical `countWords()` rule used by the candidate counter; derived counts are not persisted.
- Visible written text is transiently staged and committed at navigation, submission, lifecycle and timer checkpoints so a hard deadline cannot drop the last legal draft. Checkpoints replace the current free-response value without answer-revision/keystroke telemetry.
- Practice overtime is timer time beyond the applicable frozen paper/section budget. `postDeadlineMs` attributes only visible question exposure after that advisory deadline. The Written-answers summary sums this field only across written questions; the Question-times ledger remains the all-question attribution surface. Hidden-page time and non-written questions therefore must not be misreported as written-answer overtime.

## Subject hierarchy and sections

- An **exam section** can have timing/navigation limits and includes many unrelated subjects.
- **Subject → Topic → Subtopic** is a semantic hierarchy distinct from exam sections. Repository-maintained exam taxonomies use versioned `practice-desk-taxonomy` v1 data sidecars with stable node IDs, explicit parentage, canonical labels and bounded aliases. Parent-only classification is valid; do not fabricate topic/subtopic defaults merely to make the tree look complete.
- Generic manual/ad-hoc authoring may still use explicit label paths without an exam taxonomy. Maintained content under a bound year taxonomy must resolve its authored semantic path to a real taxonomy node; exam identity never activates a hidden registry in runtime code.
- The runtime package may carry the resolved taxonomy and question-revision → deepest-node assignments. Attempt start freezes that taxonomy context with the immutable paper/question snapshot, so later taxonomy edits cannot reinterpret historical analytics.
- Source taxonomy and learner notebook labels have different attribution. Source taxonomy is frozen exam/content evidence; learner `customSubject` / `customTopic` / `customSubtopic` remain separate user annotations. Do not promote learner labels into official taxonomy or conflate observed performance with verified mastery.

## Local persistence, revision safety and backups

- `practiceDesk.history` stores compact attempts plus deduplicated immutable snapshot bodies. Transactions verify both source identity and revision where applicable.
- CAS/optimistic concurrency uses revision `0` only for a new in-memory record before its first durable write. Persisted rows and backups require revisions `1+`; stale sibling-tab writes are rejected and terminal results cannot be revived by an older emergency mirror.
- `practice-desk-backup` v6 is SHA-checked, bounded, additive and conflict-aware. It cannot authenticate a maliciously authored backup: strictly validate records, fields, structural hashes and snapshots on restore.
- Corrupted or missing snapshot references should be surfaced or quarantined, not silently replaced with newly computed key/marks. Explicit deletion/discard, stable archive IDs and recovery precedence apply.
- Drafts/staging and local browser History are **separate export lifecycles**; noncanonical historical formats are not migration targets; do not promise implicit remote synchronization.
- The exam-screen **Saving… / Saved / Save problem** state observes the existing queued durable-write count and storage lock. It is presentation only: it starts no new write and does not turn explicit unsaved response fields into persisted evidence.

## Completed-attempt Study Handoff

- `practice-desk-study-handoff` v1 is an explicitly invoked **single completed-attempt** representation, not a backup, History API or learner-focus packet. Its builder receives one `GenericAttempt` and has no capability to enumerate other History.
- Inclusion controls independently cover frozen question/stimulus text, saved candidate responses, expected responses, immutable marks/verdicts, foreground time, review flags and candidate annotations. Eliminations/highlights are off by default. Saved free-response text can contain anything the learner typed, so users may exclude candidate responses.
- Expected responses are a hard builder-level capability: if the frozen paper has `allowReview:false`, requesting them still produces no expected-answer field. UI disabling is only a second presentation guard.
- Attempt ID, account identity, device information, calendar timestamps, other attempts, learning history, worked explanations, reviewer notes, source URLs and binary media are outside the handoff. Question/paper revision IDs remain so an external study tool can identify the frozen evidence being discussed.
- Question/context export follows the frozen candidate-visible representation: RichDocument text plus math `linearText`, accessible image alternative text without binary media, and frozen taxonomy subject/topic/subtopic labels when an exact assignment exists. JSON and Markdown serialization enforce their output bound at the serializer boundary as well as builder truncation; Markdown chooses a fence longer than any backtick run in exported content. A pathological oversized attempt is truncated only at a whole-question boundary and reports `includedQuestions / totalQuestions`; no export path mutates the completed attempt.

## Learner-to-authoring evidence

- `practice-desk-learner-focus` v1 is an **opt-in derived export**, not a new History store. It is scoped to exactly one `examId` and a declared `asOf` timestamp; unrelated exams, identity/account fields, device information, candidate scratch annotations and unrestricted raw History are outside the contract.
- `mode: focused` contains bounded aggregate observations only: semantic classification, observed attempt/answer counts, repeated exact-revision misses, measured slow/revisit/flag evidence, bookmarks, currently-due FSRS counts, observed accuracy and an explicit 30-day recent window where evidence exists. It never contains prior question bodies or selected responses.
- `mode: detailed` is a separate explicit consent level. It may add bounded question-revision identity/hash, prompt, **wrong non-free-response** selection/value plus readable text, measured timing/visits, flags, self-reported error label, bookmark/FSRS review state and source explanation. Correct responses and learner-authored free-response text are not exported.
- `intent: exam-simulation` means `compositionPolicy: blueprint-first`; personalised evidence cannot alter required mock coverage/weighting. `targeted-practice` means `focus-first-with-blueprint-guardrails`. Both modes instruct the author to create fresh transfer items rather than repeat prior questions.
- The reducer may state measured observations such as repeated misses or slower-than-usual timing; it must not infer a cognitive cause such as “does not understand” or “conceptual confusion”.
- A standard `practice-desk-authoring-brief` has `learnerFocusIncluded:false` and no learner block. Personalisation validates exact exam identity, inserts the validated packet plus its intent, and otherwise preserves the canonical brief unchanged. Browser and CLI use the same transformation.

## Transactional maintained-corpus writes

- `question-bank-corpus.mjs add-paper` / `append-revision` currently target maintained **custom mocks** only. Source/Reviewed/PDF provenance keeps its dedicated publication path.
- Inputs are canonical authoring source + publication-ready layered quality review + publication-ready blueprint. A bound year taxonomy is loaded from the maintained manifest graph and the authored classification must resolve through it.
- A dry run stages and validates the complete prospective corpus without mutation. A real operation uses an exclusive corpus lock, manifest-byte preconditions, create-only directories, atomic manifest replacement, final catalog validation and rollback of its own writes on failure.
- `append-revision` requires a strictly higher custom revision and never overwrites an existing edition. `add-paper` creates one self-contained paper folder plus one year-manifest entry; moving `currentPaperRef` is a separate explicit `--set-current` choice.

## Authoring and external sources

- AI/human source: `practice-desk-authoring` v1, with explicit origins, section/subject differentiation, explicit `subject` / optional `topic` / optional `subtopic` labels, stable question IDs, author-supplied explanations, question-kind keys and declared scoring. Choice questions carry 2–26 options; matching carries 1–26 items per side. Paper scoring includes correct/incorrect/unanswered marks plus optional decimal precision and per-kind rules; sections and questions may supply `scoringOverride`. Runtime precedence remains question override → section override → question-kind rule → paper default, and free-response uses that resolved positive mark as its manual assessment ceiling. Physical section definitions own their timer budgets; questions only reference their assigned section. Optional `practiceModes` narrows eligible runtime modes but does not encode an exam-specific profile. Authoring drafts may also supply generic candidate reference resources; the canonical compiler validates their rich content/media, computes their content hashes and emits the corresponding paper bindings. The canonical compiler emits `practice-desk-exam` v1. There is no second simple-bank runtime format.
- Source can be staged in bounded batches and selectively authored/published (maximum published/draft question count is enforced by validators; large imports must be split). Publication must be atomic with valid hashes, keys, source-hash-bound provenance and candidate-only separation.
- Blind quality review, quota blueprint, original/reviewed editorial mapping and supplied-document/PDF manifests have their own versioned sidecars and source-bound freshness. A maintained authoring edition may bind `quality-review.json` and `blueprint.json` in its paper manifest; every non-null binding is re-audited against the exact current source and must be publication-ready. **These sidecars do not override answer key schemas or act as independently authenticated official sources.**
- Repository-maintained exam data lives under `question-banks/`. Exam/year data may include `taxonomy.json`; generic source/engine code contains no APFC/PFRDA syllabus registry. `question-banks/catalog.json` is deliberately family-level: it owns only stable family identity, root-manifest address and `preinstalled`. Exam/year/paper manifests are the single authority for paper discovery, PYQ/mock classification, canonical edition, source/package paths and any bound quality/blueprint evidence. A preinstalled canonical maintained mock backed by an authoring source must bind passing `quality-review.json` and `blueprint.json` sidecars; missing, null, stale or publication-incomplete evidence rejects catalog loading. Canonical authoring sources are distinct from generated `.exam.json` packages and recovery archives. Catalog preinstallation is a build-time inclusion decision, not provenance certification.
- External agents can read provided files and create new outputs with permission, but cannot read private IndexedDB or fetch authenticated laws inside the offline app; one-off outputs do not silently enter Library.

## Truth and evidence boundaries

Hashes establish **internal consistency, not publisher identity**; a PDF page census or printed-key claim is an agent assertion until independently checked. Current law, primary-source provenance, figures, formulae and answer accuracy require real external evidence. FSRS scheduling and scored attempts are separate; revision cards do not revise History results. FSRS review rating/timestamp are replay truth; duration is separately measured foreground evidence with recall/post-reveal phases and interruption reliability. Optimizer profiles report raw source review/card counts separately from converter-retained item/card counts; evidence floors apply to retained optimizer evidence. Physical Safari/mobile/assistive technology is not proved by cross-platform emulation alone.
